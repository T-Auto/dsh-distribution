# DIST-008 — Host Coexistence（同主机多环境运行时隔离）

Status: Draft
Scope: 同一主机上并存多个 environment instance 时的**运行时行为义务**；不定义单例机制、进程管理 API、沙箱或安全边界
Coordinates: 无（本提案不新增 `apiVersion + kind`，见 "Normative change"）

## 为什么需要

DIST-001..007 覆盖了环境"如何向外部说明自己"：身份（DIST-001）、组成（DIST-002）、资源归属（DIST-003）、发现（DIST-004）、状态观察（DIST-005）、迁移（DIST-006）、可枚举入口（DIST-007）。这些协议都允许同一台主机上存在多个 environment instance，LAYOUT 也要求把资源归属说清楚。

但它们都不回答一个更基础的问题：**这些环境的运行时同时跑起来的时候，彼此的边界在哪里。** 描述得再清楚，也不会让两个运行时互不干扰。已观察到的互相破坏形态有三类（以下为通用模式描述，不指向任何具体产品）：

1. **以发行物/产品身份为键的主机级单例**。运行时的"同一时刻只有一个实例"仲裁（具名互斥量、窗口类名、IPC 名、通知区身份等）只用了产品标识作为键，没有环境区分。结果：环境 A 在运行时启动环境 B，B 无法启动，甚至把 A 的界面抢到前台——两个本应互不相干的环境互相排斥。
2. **子进程未绑定 owner 生命周期**。运行时为该环境启动的托管进程/子进程没有随 owner 一起终止。owner 崩溃或被强制结束（清理代码根本不会执行）后留下孤儿进程，继续持有该环境独占的写句柄（会话存储、数据库、锁），于是该环境下一次启动失败并报告"已被占用"，而人工排查时只看到"环境已关闭"。
3. **按共享 OS 属性批量识别并终止进程**。为"清理自己的环境"而按镜像名、可执行文件名、窗口标题或命令行子串枚举并结束进程。因为多个环境的运行时往往来自**同名二进制**，这类匹配会杀掉另一个环境的运行时；又因为调用链上的解释器/工具进程会携带同样的路径或名称，甚至会杀掉发起清理的那个进程本身。

这三类问题的共同点是：**它们不能靠"多写一份声明"防住**，只能靠运行时实现的行为义务。因此本提案定义义务，不新增坐标，也不声称声明能证明隔离。

## 运行时隔离义务

**COEX-01（范围与定位）**：本提案适用于同一主机上并存一个或多个 environment instance 的运行时与管理局（整合包自带 runtime、启动器、管理器、托管进程）。条款是**运行时行为义务**，MUST NOT 被解读为"在描述符里声明了归属就等于隔离"，也 MUST NOT 被当作 OS 安全沙箱要求（沿[架构 §6](../architecture.md) 与 LAYOUT-05）。声明的作用是让工具**发现**边界；边界是否真的成立 MUST 由实现提供证据（见 [conformance](../../conformance/README.md) 分层第三层）。

**COEX-02（单例键必须是环境实例）**：任何承担"同一时刻只允许一个"语义的主机级单例资源——具名互斥量/锁、IPC 端点、窗口类或窗口名、通知区身份、单实例仲裁文件、独占的浏览器/WebView 用户数据目录等——MUST 以**环境实例身份**（该实例的 `instanceId`，或该实例独占的 root 派生的稳定值）作为键。

- MUST NOT 只以发行物 id、产品名、可执行文件名或安装包标识作为键。
- 两个不同 `instanceId` 的运行时 MUST 能够同时存在并各自正常启动；它们 MUST NOT 互相排斥、互相阻塞或互相唤醒。
- 本提案不规定键的构造方式（摘要、路径派生、句柄继承等均可）；规定的是**区分粒度必须到实例**。

**COEX-03（同一实例重复启动的收敛）**：同一个 `instanceId` 被第二次启动时，实现 MUST 把行为收敛到该实例自身：还原/聚焦它自己的界面，或明确拒绝并给出可执行的诊断信息。

- MUST NOT 因此启动第二个写者去写该实例同一份独占状态（会话存储、数据库、锁、缓存、凭据）。
- MUST NOT 因为"该实例已在运行"而去激活、聚焦或唤醒**另一个实例**的界面或进程。
- 收敛失败时 MUST 报告失败，MUST NOT 静默降级为"再开一份"。

**COEX-04（子进程生命周期绑定 owner）**：运行时为其环境启动的子进程树 MUST 绑定到该 owner 进程的生命周期。owner 正常退出、崩溃或被强制终止后，这些子进程 MUST 一并终止，或至少 MUST NOT 继续持有该环境独占的写句柄、锁或监听端点。

- MUST NOT 把"正常退出路径中的清理代码"当作唯一手段：强制终止不会执行清理，这条义务在**非正常死亡**下同样成立。
- 实现可以选用任何等价机制（进程组、作业对象、监督进程、句柄继承等）；本提案不规定机制。
- 环境"看起来已关闭"与"真的不再持有独占状态" MUST 一致；MUST NOT 让下一次启动因此失败。

**COEX-05（进程识别与停止只允许使用独占可证明资源）**：要停止某个环境的运行时，实现 MUST 只依据该环境**独占且可证明**的资源：环境 root、由它自己创建并记录的句柄/PID/令牌、或同等强度的归属证据。

- MUST NOT 按镜像名、可执行文件名、窗口标题、命令行子串、显示名等**跨环境共享的 OS 属性**做批量枚举或批量终止。
- 命令行包含某个路径 **不构成**归属证明：调用链上的 shell、解释器、测试运行器等进程会携带同样的字符串。
- 管理器 MUST NOT 停止非自身管理或未获授权的环境；无法证明归属或缺少权限时 MUST fail closed（拒绝操作并给出诊断），MUST NOT 先猜测再动手。

**COEX-06（可变运行时状态的位置）**：每个环境的可变运行时状态——锁、实例记录、IPC 端点、窗口/通知区身份、日志、缓存、浏览器/WebView 用户数据、临时文件——MUST 位于该环境独占的位置（沿 DIST-003 的 `exclusive` 语义）。MUST NOT 存放在按产品/发行物身份命名的**主机共享**位置（例如主机级固定目录）。

- 确需共享的位置 MUST 在 layout 中声明为 `shared`，且 MUST NOT 承载单实例仲裁状态或该环境独有的可变状态。
- 两个实例的同类状态 MUST NOT 互相覆盖；删除一个实例的运行时状态 MUST NOT 影响另一个（沿 DIST-002 的实例身份语义）。

**COEX-07（主机共享位置只可操作自有内容）**：主机级共享位置（全局发现指针、共享索引键、共享命名空间下的登记项等）MUST NOT 因为卸载、清理或"重置"单个环境而被删除或清空；只允许移除该环境自己的条目或值（沿 LOD-09）。

- MUST NOT 以"释放资源"为理由删除或改写其他环境的锁、实例记录或运行时状态。
- 共享载体自身的生命周期 MUST NOT 绑定到任何一个环境的安装状态。

**COEX-08（非正常死亡后的自恢复）**：单例锁、实例记录与端点登记 MUST 在 owner 非正常死亡后自行失效，MUST NOT 要求人工清理主机状态。

- MUST NOT 让陈旧标记永久阻止该环境下一次正常启动；实现可用 OS 自动释放的锁，或带存活校验（liveness）的记录。
- 回收与清理 MUST 幂等、可重试；崩溃恢复过程中 MUST NOT 影响其他环境的运行与启动。
- 恢复失败时 MUST 给出可执行的诊断（哪个环境、哪个资源、建议动作），MUST NOT 只报告"启动失败"。

**COEX-09（共享命名空间资源冲突）**：端口、socket、IPC 名、通知区槽位等共享命名空间资源发生冲突时，实现 MUST 重试、退避、迁移到新资源，或 fail closed 并报告。

- MUST NOT 通过终止持有该资源的**非自身**进程来"解决"冲突。
- MUST NOT 假定某个固定端口或名称可以被自己独占；声明中的位置不构成保留（沿 LAYOUT-05）。

**COEX-10（证据与诚实声明）**：本提案全部条款属于**运行时行为义务**，落在 conformance 分层第三层（implementation evidence）。本仓库不提供执行器，因此：

- MUST NOT 由结构校验、语义校验或本仓库测试通过推断这些条款成立；
- 实现方 MUST NOT 用"描述符里声明了 exclusive/隔离""仓库测试全绿""文档已写明"作为运行时隔离证据；
- 隔离证据 MUST 来自被测 revision 上的实际实验，至少覆盖：两个不同实例同时运行互不干扰、同一实例重复启动收敛、owner 被强制终止后子进程与独占句柄的释放、共享命名空间冲突下的行为、以及按共享 OS 属性批量终止的防护。

## Status, Scope and boundaries

- Status: Draft；拟议公共契约，未被生态治理接纳为 Stable。
- Scope：只定义同主机多环境并存的运行时行为义务，以及这些义务的证据归属。
- 明确不在范围：单例/进程管理/沙箱的具体机制与 API；OS 安全边界或恶意代码防护（本协议不构成安全隔离证明）；管理器如何选择被管理环境；准入、市场与治理（属生态项目）。
- 明确不做：不新增协议坐标或文档 kind；不要求任何产品改名、改目录或改启动方式；不把实现细节写成规范性要求（条款只约束"区分粒度**到实例**""归属证据强度""状态位置归属"这些可移植性质）。

## Normative change

新增行为义务条款 COEX-01..10，**不新增协议坐标、不新增文档 kind、不修改 DIST-001..007 的任何既有语义或坐标**。

不新增坐标是有意的：把"运行时隔离"做成一份可声明的文档类型，会诱导实现用"文件存在"冒充"边界成立"，而这正是本仓库在架构 §6 与 LAYOUT-05 中明确拒绝的推理。隔离是运行时性质，不是文档种类；本提案因此以义务形式存在，并由 conformance 矩阵标记其证据状态。

## Compatibility impact

向后兼容：不改变任何现有 schema、validator 或 wire 语义，既有实现无需改动即可继续通过结构/语义校验。

对实现的影响是**行为侧**的：已经做到按实例区分单例、绑定子进程生命周期、只按独占资源识别进程的实现无需改动；未做到的实现需要修复，否则会在同主机多环境场景下违反 COEX-02..09。

## Evidence / Fixtures

- 本提案不引入 schema 或 fixtures：没有可离线判定的结构，条款全部依赖真实运行时行为。
- 纯语义测试无法证明这些条款（沿用 conformance 分层；见 [一致性矩阵](../../conformance/README.md)）。
- 实现方证据要求见 COEX-10：必须在被测 revision 上提供双实例、重复启动、强制终止、冲突与误杀防护的实测记录，并注明 OS/版本、命令、退出码与未覆盖项。
- 本仓库对这些条款一律标记 **not-tested**，不得报告为已通过。

## Conformance impact

在 [conformance requirement matrix](../../conformance/README.md) 增加 COEX-01..10 行，证据来源标注为 "proposal（无 schema）"，实现层行为一律 not-tested。本提案不影响 `checkDescriptor` 对未知协议的处理，也不改变任何现有 requirement 的结论。

## Migration

无既有迁移。既有环境不需要数据迁移；实现只需在自身运行时修正单例键、子进程生命周期与进程归属判定。已发布的 descriptor 与 layout 声明保持有效。

## Rollback

撤回本提案即回到"协议只描述环境、不约束并存行为"的状态，不涉及数据或格式回滚。已经按 COEX 修正的实现可以保留修正（更严格的实例隔离不与任何既有条款冲突）。
